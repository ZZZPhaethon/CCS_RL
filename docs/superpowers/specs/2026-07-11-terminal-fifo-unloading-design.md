# 终端 FIFO 卸载设计

## 目标

将先进先出（FIFO）卸载设为所有终端共享的物理层规则，使 RL、规则基线、MILP/MPC、LLM 和 replay 控制器都必须遵守。允许多艘船同时停靠或等待，但每个终端在每个仿真时步最多只能卸载一艘船。

## 必需行为

- 每个终端维护一个持久化 FIFO 队列，队列成员是已停靠且载货量大于零的船舶。
- 新满足条件的船第一次被观测到停靠在该终端时，加入队尾。
- 队首船部分卸载后，只要仍停靠在终端，就继续保持队首位置。
- 船舶在未卸空时离港，应立即离开队列，下一艘船成为可卸载对象。
- 该船日后载货返回时，应作为一次新的到达加入队尾。
- 如果多艘新船在同一仿真时步首次被观测到达，则用 vessel ID 作为确定性的平局规则。
- 当终端可用泊位数为零时不得卸载；只要可用泊位数大于零，每个终端仍然只允许一艘队首船卸载。

## 架构

`PhysicalState` 新增 `terminal_unload_queues: dict[str, list[str]]`，使队列顺序可以随状态复制、快照、控制器切换和 replay 保留下来。终端开始处理卸载前，物理操作根据当前船舶泊位和载货量同步队列：移除不再符合条件的旧成员，并把新符合条件的船加入队尾。

`operations/unloading.py` 是最终约束边界。显式的 `unload_vessel` 请求只有在目标船为当前队首时才允许执行。若请求卸载另一艘已经停靠的船，则将请求裁剪为零，并记录 `fifo_unload_required` 违规。未指定船舶的旧式 `unload_tph` 请求自动作用于队首船。因此，任何控制器都不能通过提交另一个 vessel ID 绕过 FIFO。

控制器侧的船舶选择只是提前生成可执行动作。`CCSEnv` 和 `RuleBasedActionGenerator` 应读取共享队首，从而正常情况下不会产生无效动作；无论动作来自哪个调用方，物理卸载操作始终是最终权威。

## 状态与数据流

1. 船舶运动更新 `PhysicalState.vessel_berths`。
2. 下一次物理步根据泊位和载货状态同步各终端 FIFO 队列。
3. 动作解析器保留请求的终端卸载动作。
4. 卸载操作检查泊位可用性和 FIFO 合法性。
5. 每个终端最多只有队首船向终端转移货物。
6. 结果状态连同队列顺序一起被正常复制和序列化。

无需增加到达时间戳。持久化队列顺序足以区分不同时步到达的船；只有同一同步过程中出现多艘此前未入队的船时才进行排序。

## 兼容性与范围

- `terminal_unload_queues` 使用空字典作为默认值，因此已有 `PhysicalState(...)` 构造方式保持兼容。
- 船舶动作空间、observation 结构、航线运动、终端库存、管输、注入和已训练策略参数均不改变。
- `berth_count` 不再作为终端中可表示船舶数量的上限，只用于判断卸载服务是否可用；每个终端的卸载并发数固定为一艘船。
- 现有显式卸载动作仍保留目标船语义，但非队首目标在物理上不可执行。
- 队列必须包含在 `PhysicalState.copy()` 和 `PhysicalState.as_dict()` 中，以支持确定性的 replay 和审计。

## 违规类型

- 当请求的船舶未停靠在终端时，继续使用 `berth_required`。
- 当显式请求一艘已停靠、仍有货但不是队首的船时，记录 `fifo_unload_required`。
- 现有 `flow_clipped` 继续用于载货量、卸载速率和终端剩余容量导致的流量裁剪。

## 验证要求

自动化测试必须证明：

- 到达顺序优先于 vessel ID 顺序；
- 多艘船停靠时只有一艘船卸载；
- 部分卸载后的队首船不会被抢占；
- 未卸空的队首船离港后会出队，下一艘船前移；
- 离港船返回时加入队尾；
- 显式请求非队首船会被拒绝，并产生 `fifo_unload_required`；
- 队列状态能够正确复制和序列化；
- 现有物理层、环境、规则基线、replay 和控制器测试保持通过。
